# The scan is the only requester — 1 November 2026

Junid's model: stock leaves a location only through a sale. A request to Central or a hub is raised **only** by the hourly refill scan, comparing on-hand against policy. A Solve is not a request; it places a product's policy batch.

## COMMIT 1: what no longer writes a request

| Path | Before | Now |
|---|---|---|
| **On hold** ("Coming Tomorrow", `src/App.jsx`) | Wrote a `/refill_requests` row against the order's hub (`via: "on_hold"`, 1,009 rows all-time). | Writes nothing. The hold is the customer-facing status only: warehouse tab, TV row, status page and the `orderTomorrowNotify` WhatsApp. Releasing a hold still withdraws an ask raised before today. |
| **Website-order escalation** (`scripts/shopify/onlineOrders/escalate.mjs`, the Mac mini poller) | A line not found raised a Hub 2 → shop "Shop Refill card" and a Central → hub refill row (`via: "online_escalation"`, 27 rows). Junid's 25 Oct exception. | **Revoked.** No chain starts, and a failed line waits on the order's needs-attention list. A chain already under way stops on the next tick. Its open request is left for the one-off script below to decide. Junid's own Settings override ("mark unavailable" / "resolved by hand") still works. |
| **"Order it now"** (POS button → `orderNowRequests.mjs`) | Re-checks live stock and routes the line to stock that exists (a pick, not a refill). Releases only the online order's piece of an open request. | **Kept.** It never creates a request and never bypasses policy. |
| **Missing Sneakers "Request"** (`src/components/stock/MissingFootwear.jsx`) | Raised a request for whatever quantity staff typed (`via: "missing_sneakers_pick"`). | **Off.** A typed quantity bypasses policy, by Junid's own test for "Order it now". The button is replaced by a note pointing to **Solve**, which uses the policy quantity and stays. |

### The guard
- Every request carries `requestSource`: `"scan"` (refill-scan.cjs, live rows and SHDWrr- previews) or `"solve"` (the clothing Solve, its Hub 2 leg, and the Missing Sneakers Solve).
- `refillRequestSourceGuard` (new function, `functions/lib/request-source.cjs`) checks every **new** `/refill_requests` row. Rows written before the tag existed are recognised by their shape.
- Anything else is cancelled while untouched (`cancelReason: "not_scan_source"`) and logged for Junid at `/refill_engine/rejectedRequests/{id}`.
- A tag can't be spoofed: `"scan"` needs the engine's shape, and `"solve"` needs a Solve's.
- A row someone has started sending is never cancelled, only logged.

### Open requests from those two paths (live, 1 Nov)
See the PR body for the before/after table. The one-off `scripts/refill/scan-only-cancel.mjs` judges each row the way the scan would: the engine's own `resolveTarget` against on-hand plus every other open request to that cell.

### What Junid loses with this
- The **"now available" hold WhatsApp** (`holdAvailabilityNotify`) fired when a hold's request was fulfilled. New holds raise no request, so that message no longer goes. The "coming tomorrow" message at hold time still does.
- Website lines no longer travel by themselves. Staff use **Order it now** once the scan's refill has landed.
